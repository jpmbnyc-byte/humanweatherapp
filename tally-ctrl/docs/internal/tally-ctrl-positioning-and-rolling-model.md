## 1.9 AI identity disclosure rule

**✅ CONFIRMED — July 2026.** This is a config setting, not a per-message judgment call.

**The boundary is authorship, not tooling.**

| Mode | Definition | Disclosure |
|---|---|---|
| **Drafting** | Agent composes; JP Bobo reads the message in full and presses send | **None required.** JP is the author. A drafting tool is not a speaker. |
| **Conversational** | Agent generates and sends a reply without JP reading it first | **Required**, in the first agent-generated message of the thread |

**Sprint OS config block:**

```yaml
ai_identity_disclosure:
  default_mode: drafting            # human-in-the-loop; no disclosure
  drafting_mode:
    sender: "JP Bobo"
    disclosure: none
    requirement: JP must read full message body before send. No batch-approve.
  conversational_mode:
    disclosure: required
    line: >
      Note: this reply was generated by an automated assistant.
      JP Bobo reviews every thread and will follow up personally.
    placement: first agent-generated message in thread
  hard_rules:
    - Agent NEVER claims to be JP Bobo.
    - Agent NEVER claims or implies it is human.
    - Agent NEVER denies being automated if asked, in any phrasing.
    - Direct question about whether sender is human -> ESCALATE, no autonomous reply.
  escalation_inherits: true         # all §escalation triggers apply here too
```

**The rule that does the real work:** *"JP must read the full message body before send. No batch-approve."* Drafting mode is only honest if the review is real. A one-click approve-all across a wave converts drafting into conversational mode without anyone deciding to, and the disclosure obligation attaches whether or not the config says so.

**Reference points** (confirm with counsel — not legal advice): California's bot disclosure law, B&P §17941, covers automated communications intended to incentivize a sale and is the most relevant statute if soft-market expansion reaches CA. Utah's AI Policy Act requires disclosure on request. Neither is triggered by drafting mode as defined above; both are triggered by conversational mode. The `hard_rules` block is written to satisfy the strictest reading of either.

# PART 2 — ROLLING INTAKE MODEL

## 2.1 Why the current design breaks

The founding 10 is a **batch**. Batches have an end state: at day 80, all ten accounts have completed the cadence and there is no work left. Momentum collapses precisely when the campaign has finally built enough asset library and message discipline to be efficient.

Worse, a batch produces a lumpy pipeline — every account reaches the decision window simultaneously, so a bad wave means a dead quarter with nothing behind it.

The fix is to convert the campaign from a batch into a **rolling wave system** with continuous intake, a hard WIP cap, and a perpetual tail.

---

## 2.2 The two-lane wave model

**✅ CONFIRMED — soft markets are invited in, not rejected.**

Geography is a *marketing* constraint here, not a delivery constraint: the Snapshot is explicitly desk-review with no site visit, and the Diagnostic deliverable is an exposure schedule and an ASC 606 memo. None of that requires proximity. What proximity actually buys is referral density and affordable physical touch — so out-of-region groups get a cheaper lane rather than a rejection.

### Lane definitions

| | **CORE lane** | **SOFT lane** |
|---|---|---|
| Geography | NJ, NY, PA, CT, MA, DE, MD | Everywhere else (VA, NC, OH, and outward) |
| Cadence | Full 12 stages, 80 days | 6 stages, 55 days |
| Channels | Email, LinkedIn, phone, physical | Email + LinkedIn only |
| Physical touch | Per §2.5 tiering | **None.** Digital Ledger PDF only |
| Registers | Controller + Principal + CFO | Controller only |
| Touch events/account | ~17 | ~7 |
| Load per week | 1.5 events | 0.6 events |

### Intake rates

| Lane | Wave size | Interval | Per year | Steady-state active |
|---|---|---|---|---|
| Core | 3 | 14 days | 78 | ~17 |
| Soft | 2 | 14 days | 52 | ~6 |
| **Total** | **5** | **14 days** | **130** | **~23** |

**WIP cap (hard): 24 active accounts, both lanes combined.**

**The arithmetic:**
- Sustainable solo outbound capacity, AI-assisted drafting with real human review: **~35 touch events/week**
- Core lane: 17 accounts × 1.5 = **~25 events/week**
- Soft lane: 6 accounts × 0.6 = **~4 events/week**
- Quarterly tail reserve (growing): **~6 events/week rising to ~10**
- Total: **~35 events/week** — at capacity, by design

Annual intake rises from 104 (v1.0, single lane) to **130** while total weekly load is unchanged. The soft lane is free capacity because it drops the four most expensive stages.

### The promotion rule — this is the point of the design

> **Any SOFT-lane account that replies is promoted to CORE immediately and enters the full 12-stage cadence at stage 5.**

Soft markets function as a cheap, wide discovery layer. You spend nothing on physical touch or phone time until an account has shown a signal by responding. Then it graduates and gets the expensive treatment it has earned.

This is the one place where Cardone's instinct and the ABM thesis actually agree: cast wide at low cost, then concentrate hard on the responders. Promotion is the mechanism that reconciles them.

**Demotion:** none. A promoted account that goes quiet stays in CORE through stage 12, then enters the quarterly tail like any other.

### Ramp schedule

| Period | Core | Soft | Rationale |
|---|---|---|---|
| Months 1–3 | 4 / 2wks | 2 / 2wks | Tail is empty; use the free capacity to build the base |
| Months 4–12 | 3 / 2wks | 2 / 2wks | Steady state |
| Month 13+ | 2 / 2wks | 2 / 2wks | Tail load has grown; protect core quality first |

**WIP cap governance:** if a wave would push combined active accounts above 24, **the CORE wave ships and the SOFT wave is delayed.** Never the reverse, and never by shrinking research quality — the gate is what makes stage 1 work and it is not the variable that flexes.

## 2.3 Entry scorecard

No account enters a wave without clearing all five gates. This is the existing research gate, formalized and extended so it can be applied by an agent without judgment calls.

| # | Gate | Threshold | Fail = |
|---|---|---|---|
| 1 | **Scale** | CORE: 5+ rooftops · SOFT: 8+ rooftops | Reject |
| 2 | **Geography** | Determines lane, never rejection — see below | — |
| 3 | **DMS identified** | CDK, Reynolds, Tekion, DealerTrack, or Auto/Mate confirmed with source | Hold until confirmed |
| 4 | **Contact map** | CORE: Controller + one of {CFO, Principal}, both verified · SOFT: Controller only | Hold until confirmed |
| 5 | **Live signal** | One verified fact + source URL, dated within 90 days | Reject from this wave; re-queue |

**Lane assignment (gate 2):**

```
IF state IN (NJ, NY, PA, CT, MA, DE, MD)        -> CORE
ELSE IF rooftops >= 8                            -> SOFT
ELSE                                             -> reject
```

The higher rooftop floor on SOFT is deliberate. You give up phone, physical touch, and multi-threading in that lane, so the account has to be large enough that a controller-only email cadence can carry it alone.

**Gate 5 is NOT relaxed for SOFT.** The research gate is the reason stage 1 gets read, and it is the last thing to weaken when reaching into unfamiliar geography where you have no referral credibility to fall back on. If anything it matters more there.

**Signal types that qualify for gate 5, in descending order of strength:**
1. **Acquisition or divestiture** — an acquired rooftop is cost-normalization chaos by definition. Strongest possible trigger.
2. **DMS migration announced** — data mapping is where cost basis breaks.
3. **New Controller or CFO hire** — new person, wants a clean baseline, no ownership of the prior error.
4. **New rooftop opening / franchise award**
5. **Fixed ops or recon center consolidation**
6. **Leadership commentary on gross compression** — public statement, earnings, trade press

## 2.4 Sourcing pipeline

The wave model dies if intake starves. Four named, renewable sources — each should yield enough for at least one wave per month.

| Source | Yield | Cost | Notes |
|---|---|---|---|
| **Automotive News Top 150 Dealership Groups** | High | Subscription | Ranked by units. Filter to Northeast, 5+ rooftops. Refreshed annually. |
| **State association member directories** — NJ CAR, GNYADA, PAA, MSADA, CT Auto Retailers | High | Free / membership | Also the partner channel. Dual-purpose. |
| **Kerrigan Advisors quarterly Blue Sky Report + Haig Report** | Medium, very high quality | Free | M&A activity = gate-5 signal #1, delivered quarterly. This is the single best trigger source available. |
| **20 Group rosters** (NCM, NADA) | Medium | Partner-dependent | Requires the partner conversation first. Highest-trust source once open. |
| **DMS user conference attendee lists** | Low | Variable | Opportunistic only. |

**Soft-lane sourcing:** the same sources, geography filter removed. Automotive News Top 150 is national by construction, Kerrigan and Haig report M&A nationally, and every state has a dealer association directory. Soft-lane intake is not supply-constrained — it is capacity-constrained, which is what the WIP cap is for.

### Contact mapping — the $0 stack (replaces Sales Navigator)

LinkedIn Sales Navigator was specified in v1.0 at ~$100/mo and is **removed**. Two reasons: it returns names and titles but no email addresses, so it was never the real line item; and its coverage of this specific persona is poor. Long-tenured dealership Controllers and Office Managers frequently have no LinkedIn presence at all.

| Layer | Source | Cost | Job |
|---|---|---|---|
| **Primary discovery** | Dealer staff pages — `/staff/`, `/meet-our-staff/`, `/dealership/staff.htm`, `/about-us/our-team/` | $0 | Names, titles, department, often direct email + extension. Auto retail publishes its full roster publicly; almost no other B2B vertical does. |
| Group leadership | Corporate/group site Leadership page | $0 | CFO, Corporate Controller, Principal |
| Gap fill | Google X-ray: `site:linkedin.com/in "controller" "<Group Name>"` | $0 | The ones who do have profiles |
| Ownership verification | State entity filings — NJ Div. of Revenue, NY DOS, PA Dept. of State | $0 | Officers and principals, authoritative |
| Confirmation | Phone the main line: *"Who handles the accounting office for the group?"* | $0 | Dealerships are retail and answer their phones. Highest accuracy of any method. |
| Email construction | Hunter.io **free tier** — verification only | $0 | See credit rule below |

**Credit rule — do not run Domain Search.** It bills per email returned; you would burn ~15 credits to get the 3 you want. Instead: pull one known-good address off the staff page (free) → infer the pattern (`first.last@`, `flast@`, `first@` covers nearly all dealer groups) → construct the targets by hand → spend credits on **verification only** at half a credit each. At 5 accounts/wave × ~2.5 contacts = ~25 addresses/month, that is ~13 credits against a free tier of 25–50. Comfortable.

**Upgrade trigger:** if intake ever exceeds 8 accounts per wave, evaluate **Apollo Basic ($49/mo annual, $59 monthly)** — not Sales Navigator — because Apollo bundles the email data Sales Navigator makes you buy separately. Buy monthly, not annual, until after Diagnostic conversation #3. The binding constraint that would justify it is Apollo's **sequence count**, since the free tier caps at 2 active sequences and this positioning set requires 3+ registers. Check first whether Sprint OS already handles sequencing — if it does, both tools are buying an orchestration layer you already own.

### Signal detection — Wayback staff-page diff

Run each target's staff page through the Internet Archive and diff snapshots across quarters. A Controller name that changed within 90 days is **gate-5 signal type 3**, detected free, on exactly the people who are invisible to LinkedIn job-change alerts because they have no profile. Add as a standing source under gate 5.

**Sourcing cadence:** one 90-minute research block per week produces the next wave, both lanes. Batch the research; never research inside a send day.

## 2.5 Physical touch tiering — cost control

Stages 4 and 10 are the only line items with real marginal cost. Left ungoverned, 130 accounts/year × 2 physical touches at ~$60 all-in = **$15,600/year**, which breaks the lean-spend constraint.

**Tiering rule — physical touches are earned, not automatic:**

| Prospect tier | Lane | Criteria | Stage 4 | Stage 10 |
|---|---|---|---|---|
| **Command** | Core | 15+ rooftops, or gate-5 signal type 1–2 | Full Variance Ledger, hand-numbered + grease pencil | Yes |
| **Control** | Core | 8–14 rooftops | Ledger, standard print run | Only if a reply has occurred |
| **Foundation** | Core | 5–7 rooftops | Digital Ledger PDF, personalized cover | No |
| **Soft** | Soft | Any | Digital Ledger PDF, personalized cover | No |
| **Promoted** | Soft → Core | Replied, promoted to Core | Physical Ledger sent on promotion, at Control level or above per rooftop count | Yes |

**Governed annual cost:** roughly 16 Command + 28 Control physical units, plus promoted-account sends ≈ **$3,000–3,500/year.** Within lean spend, and the scarcity is now real rather than asserted.

The soft lane costs **nothing** in print until an account replies. That is the entire economic argument for opening soft markets — you are extending reach against email and LinkedIn, which are already sunk costs, and spending physical dollars only on demonstrated interest.

## 2.6 The Ledger as a serialized asset

"The Variance Ledger — Northeast Edition, Vol. 1" was built as an edition of 10. That doesn't survive contact with a rolling model, and it shouldn't — the fix strengthens the asset.

**Convert the Ledger from a one-off artifact into a quarterly serial publication.**

| Edition | Timing | Edition size | Data basis |
|---|---|---|---|
| Vol. 1 — Northeast | Shipped July 2026 | 10, hand-numbered | Reference engagement |
| Vol. 2 | **Gated — see below** | ~20 | Vol. 1 + Estimator run data + any completed Snapshots |
| Vol. 3+ | Quarterly once Vol. 2 ships | ~20 | Cumulative |

**Why this matters strategically:** it turns the stated goal of *owning the Ledger as a proprietary data asset* from an aspiration into a production schedule. Every Estimator run, every Snapshot, every Diagnostic adds rows. Vol. 6 is materially more credible than Vol. 1 because it is built on a larger n, and no competitor can assemble that dataset retroactively.

### ⚠ Vol. 2 is gated on print approval, not on a date

**Decision, July 2026: no production date is set. Vol. 2 ships when the print version meets JP's standard, and not before.**

This is the correct call — the Ledger is the highest-craft object in the funnel and a print run JP isn't happy with damages the asset it exists to build. But it creates a dependency that v1.0 got wrong, and the fix is structural:

**The quarterly tail no longer depends on the Ledger.** v1.0 specified the Ledger edition as the payload for the perpetual quarterly touch (stage ∞). That made an unbounded print decision a blocker on the compounding mechanism. Corrected:

| Touch | Payload | Depends on print? |
|---|---|---|
| Stage 4 — physical, Command/Control | Physical Ledger | Yes |
| Stage 4 — Foundation / Soft lane | **Digital Ledger PDF** | No |
| Stage ∞ — quarterly tail | **Quarterly Variance Brief** — digital, 2 pages, one teardown + one new proof number | **No** |

The Quarterly Variance Brief is a new, deliberately low-craft digital asset. It exists so the tail always has a payload and never becomes a "checking in" email. It is not the Ledger and should not look like it — different template, different name, no numbering.

**Resolving the print gate.** "Not sure yet" is not a schedulable state, so convert it into a spec with a decision date:

1. **Name the variables** — paper stock and weight, binding method, page count, trim size, whether hand-numbering and grease pencil survive at 20 units, single vs. two-colour
2. **Two vendors, physical proofs** — one short-run letterpress/specialty printer, one production digital shop. Proofs, not PDFs; the decision is tactile and cannot be made on screen.
3. **Set a decision date, not a ship date** — the date by which proofs are in hand and judged. Vol. 2 ships 4 weeks after approval.

Until that date exists, the Ledger is a Command-tier physical touch only, and nothing else in the model waits on it.

## 2.7 What actually compounds

Four mechanisms, in order of impact:

**1. The perpetual tail.** No account exits on non-response. Accounts move to quarterly, forever. The addressable base is therefore monotonically increasing: 10 accounts at launch, ~104 at month 12, ~200 at month 24. The tail is cheap — one email per account per quarter, carrying an asset that was produced anyway.

**2. Asset library reuse.** Every teardown, every objection frame, every Ledger edition is written once and serves every subsequent wave. Wave 1's stage 6 payload requires original writing. Wave 20's stage 6 payload is selected from a library of 20 teardowns, chosen for fit. **Marginal cost per account declines monotonically** while quality rises.

**3. Data density.** Estimator runs and completed engagements feed the Ledger. More data → more credible collateral → higher response rate on the next wave. This is the only mechanism here that is genuinely defensible against a competitor.

**4. Network density.** Northeast dealer groups are a small, interconnected world — the same 20 Groups, the same associations, the same CPA firms, the same acquirers. Past roughly 40 accounts touched, referral and recognition effects start doing work that outbound was doing alone.

## 2.8 Sprint OS configuration changes

To operate this, the Diagnostic Sprint OS needs six additions:

1. **`wave_id`** on every account record. Enables cohort analysis: which wave, which signal type, which register performed.
2. **`lane`** — `core` | `soft`. Set by gate 2. Determines cadence length, channel set, and register availability.
3. **`prospect_tier`** field (Command / Control / Foundation / Soft) — drives stage 4 and 10 physical-touch logic automatically.
4. **`promoted_from_soft`** boolean + `promotion_date`. On first reply from a soft-lane account, OS sets lane to `core`, entry point to stage 5, and triggers the physical Ledger send.
5. **`next_stage_due_date`** — converts the cadence from a plan into a daily queue. This is the single most important field; the daily runbook should answer "what's due today" without any thinking.
6. **`active_account_count`** with a hard block at 24, combined across lanes. If a wave would breach the cap, the OS ships the core wave and delays the soft wave.
7. **Entry scorecard as a gate**, not a checklist. An account cannot be assigned a `wave_id` until all five gates return pass with source URLs attached.
8. **Payload library** keyed by stage **and lane**, with a `last_used_wave` field so the same teardown isn't sent to overlapping waves in the same month.
9. **`ai_identity_disclosure` block** per §1.9, with `default_mode: drafting` and the no-batch-approve constraint enforced at the UI level, not by policy alone.
